Public-Key Generation on a Toy Elliptic Curve (Scalar Multiplication as a One-Way Function)

From a private key to a public key with elliptic-curve scalar multiplication, on a small toy curve, followed by a simple statistical look at the output.

1. Background

Elliptic-curve scalar multiplication is a one-way function. Given a private key k and a base point G, the public key Q = kG is easy to compute by repeated point addition (or by double-and-add). Recovering k from Q is the Elliptic Curve Discrete Logarithm Problem (ECDLP), which is believed to be computationally hard on a real curve.

The function is deterministic and efficient in the forward direction, so it shares some features with cryptographic hash functions. It is, however, used for public-key cryptography and digital signatures, not for hashing. The goal here is to understand the mechanics of scalar multiplication, not to build a secure system.

2. Task

Write a small program that takes a private key and produces the corresponding public key using elliptic-curve scalar multiplication on the toy curve y² = x³ + 7 (mod 17), with base point G = (1, 5) and private key k = 6. The program prints G, 2G, 3G, ..., kG, and the final point is reported as the toy public key. It then repeats the experiment for other scalars and base points and looks at simple statistical properties of the outputs.

3. Implementation

The code is in hw1.js. Its main parts are:

  • modInv: modular inverse through the extended Euclidean algorithm.
  • pointAdd: point addition, with doubling when the two points are equal and the point at infinity O when the points are opposite.
  • scalarMult: computes kP with double-and-add, so large k needs only about log2(k) doublings.
  • allPoints: enumerates every point of the curve, which lets us compute the order of each point.
  • avalanche and the other helpers: the statistical tests shown below.

Each curve is treated in the same way: the program prints the multiples of the base point, the toy public key, a cross-check against plain repeated addition, and the statistics. To try another curve or base point, edit the CURVES array at the top of hw1.js.

6. Discussion

Properties of a one-way function

Deterministic, efficient forward computation. Computing Q = kG takes a number of group operations proportional to the number of bits of k. This is the easy direction, and the program demonstrates it directly.

Hardness of inversion. This is the property that makes the function one-way, and it cannot be seen in these experiments. The subgroup generated by G has order n, so brute force needs at most n steps. On the toy curve n is tiny, so the discrete logarithm can be found instantly. For secp256k1 the group order is about 2256, which makes brute force infeasible.

Output distribution. A good one-way function should produce outputs that look spread out and unpredictable, so coverage, frequencies and bit balance are sensible checks. They are weak indicators, though. Over a full period each point of the subgroup appears exactly once, so the output is perfectly "uniform" over that subgroup by construction, and this says nothing about hardness. Moreover, the output must satisfy the curve equation, so not every pair (x, y) is possible and many x values have no point at all.

Correlation between input and output. The Pearson coefficients between k and the coordinates are typically close to zero, but this is misleading. The map is algebraic: (k + l)G = kG + lG, and (k + n)G = kG. Linear structure is invisible to simple correlation tests, yet it is a serious weakness for a cryptographic function. The same holds for the serial correlations between consecutive outputs, which reflect the fact that (k + 1)G = kG + G.

Avalanche. Flipping one bit of k changes the scalar by ±2i, and the change in the output is dictated by group arithmetic. Nothing forces the output to change in about half of its bits. Scalars that differ by a multiple of n give the same point, so on a small curve the periodicity lowers the average change. Compare the value in the output with the ideal 50% of a hash function.

Properties specific to hash functions

Hash functions are designed to have properties that scalar multiplication does not provide:

  • Fixed-size output for inputs of any length. Scalar multiplication has a fixed input domain (scalars modulo n) and no notion of arbitrary-length messages.
  • Strong avalanche. A one-bit change in the input should flip about half of the output bits. Here the change is determined by group structure, as noted above.
  • Collision resistance. Any hash function must have collisions by the pigeonhole principle, but they must be hard to find. Scalar multiplication is injective on the scalars 1 .. n-1, so distinct scalars never collide there. The security relies on the discrete logarithm, not on the absence of collisions.
  • No algebraic structure. Hash functions are built to avoid linear relations such as h(a + b) = h(a) + h(b). The group law of the curve is exactly such a structure.

Summary

For a one-way function, the meaningful properties are determinism, efficiency of the forward direction, and hardness of inversion. The last one cannot be tested on a toy curve. The statistical properties (distribution, bit balance) are only weak evidence on their own, and the algebraic structure makes some of them misleading. The properties specific to hash functions, such as strong avalanche and arbitrary-length input, are not expected from scalar multiplication.

Connection to Ethereum

In Ethereum, the private key is a 256-bit integer, and the public key is the point (x, y) on secp256k1. The address is then derived by applying the Keccak-256 hash to the public key and keeping the last 20 bytes. The hash-like properties therefore come from Keccak, applied after the elliptic-curve step, and not from the scalar multiplication itself.
